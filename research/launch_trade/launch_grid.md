# 放量上涨 / 放量下跌提醒参数全量搜索（2026-10-19）

不参考以前的研究结论，用全部历史 1 分钟 K 线（2021-09 起到 2026-10-19），两个方向**分别**在同一个候选族里搜索最好的一组参数。
现行 `config/default.yaml` 的取值只作为对照，不享有任何优先。脚本：`launch_grid.py`。

## 一、预先写定的口径与判据（跑数之前写下，之后不改）

### 1. 提醒好坏的度量

提醒的价值 = 提醒之后价格沿提醒方向继续走（上涨提醒之后继续涨、下跌提醒之后继续跌）。每条提醒按「跟着提醒方向做一笔」计分：

- 入场：提醒那根 K 线收盘价（即提醒价）之后再等 d 分钟的收盘价，d ∈ {0, 1, 3}（模拟看到提醒后的反应时间）；
- 出场：入场后 h 分钟的收盘价，h ∈ {10, 30, 60, 120, 240}；
- 单笔收益 = 方向 × (出场 / 入场 − 1)，截断到 ±30%（防止个别插针主导结果），再扣往返成本 0.2%；
- 提醒得分 y = 3 × 5 = 15 种入场、出场组合的平均；入场到出场之间有任何一分钟没有数据（`covered=False`）的提醒不计分，但照常参与冷却与波次。
- 日收益 x_d = 当天（UTC，按提醒时刻）所有计分提醒的 y 的平均，当天没有提醒记 0（相当于每天把资金平分给当天的提醒，没有提醒就空仓）。
- **选参指标：开发期日收益的夏普比率**（不年化的日夏普 × √365 报告）。它同时奖励每条提醒的质量和提醒的覆盖面：提醒太少的方案空仓日多，夏普自然变低。
- 活跃度下限：开发期平均每天 ≥ 2 条提醒（该方向、含第 2 波及以后），低于它的方案不参与挑选。

### 2. 数据与划分

- 合约：`contracts.json` 中全部 1149 个（含已下架），`load_data.load_series` 合并的分钟序列；`covered=False` 的分钟不判定、不计分。
- 判定一次要求基准期 + 窗口全部 `covered`。
- `check_jumps.py` 列出的 24 处价格持久跳变（多为改面值，月度文件的成交额在跳变前按当前面值估算会错）：这些合约**最后一次跳变之前**的数据全部按无数据处理。
- **开发期：2021-09-01 ~ 2024-12-31（UTC）**，只用它挑选参数、算 PBO 与 Deflated Sharpe；
- **样本外：2025-01-01 ~ 2026-10-19**，只在挑选完成后对选中方案与现行配置各算一次。

### 3. 判定逻辑

与 `LaunchDetector.add_candle`（回放口径）逐分钟一致：量比、窗口成交额、涨跌幅下限、涨跌幅上限（只因超上限失败的分钟按提醒记入冷却与再推进、不加波次）、突破、冷却、再推进、超过一个基准期从第 1 波重新计数。
脚本先拿真实的 `LaunchDetector` 在若干合约上对拍，提醒时刻完全一致才往下跑。

新增两个候选条件（现行代码没有）：

- 合约池门槛 V：提醒时该合约前 24 小时（含当前分钟）的计价成交额 > V，对应 `min_volume_24h_quote`，按方向分别搜索；
- 回吐比例上限 P（新参数）：窗口内的极值（上涨取窗口最高价、下跌取最低价）到收盘价的回吐，占窗口起点到极值这段幅度的比例 ≤ P；
  用来剔除窗口内冲高（杀跌）后已经大幅回吐、只剩收盘价勉强达标的提醒。

### 4. 候选族（两个方向各自独立、同一个族）

| 参数 | 候选值 |
|---|---|
| 窗口 W（分钟） | 3, 5, 10, 15 |
| 基准期 B（分钟） | 180, 360, 720, 1440 |
| 量比下限 R | 2, 3, 5, 8 |
| 窗口成交额下限 Q（USDT） | 5 万, 10 万, 30 万, 100 万 |
| 涨跌幅下限 C（%） | 1.5, 2, 3, 5 |
| 涨跌幅上限 M（%） | 8, 15, 不限（须大于 C） |
| 要求突破 | 否, 是 |
| 24 小时成交额下限 V（USDT） | 0, 100 万, 500 万 |
| 冷却（分钟） | 15, 60 |
| 再推进（%） | 3, 8 |
| 回吐比例上限 P | 不限, 0.5 |

每个方向 4 × 4 × 4 × 4 × 4 × 3 × 2 × 3 × 2 × 2 × 2 = 147,456 组。

### 5. 过拟合判据（全部满足才推荐，没达标直接剔除、不降级保留、不改用第二名）

1. **只用开发期选参**：选中方案 = 满足活跃度下限的候选里开发期夏普最高的一组，只此一组。
2. **Deflated Sharpe ≥ 0.95**：开发期，试验数按全部 147,456 组计，夏普方差取满足活跃度下限的候选的开发期日夏普方差，计入选中方案日收益的偏度与峰度。
3. **PBO < 0.5**：开发期按时间切成 16 段做 CSCV（12,870 种 IS/OOS 划分），IS 内同样先按活跃度下限过滤再取夏普最高者。
4. **样本外成立**：样本外日夏普 > 0 且 PSR(夏普 > 0) ≥ 0.95；入场延迟 0、1、3 分钟分别计算（各自对 5 个出场时长平均），平均每条提醒得分都 > 0。
5. **不差于现行配置**：样本外日夏普不低于现行 `default.yaml` 该方向的取值（上涨：W5、B360、量比 3、10 万、3%~15%、不要求突破、冷却 10、再推进 5、合约池 50 万；下跌：量比 4、2%~10%，其余同上涨），否则结论是维持现行配置。
   注意现行取值是用较近期的数据定的，可能与这里的样本外重叠，这一条对新方案偏严。

不测试任何按一天中时段过滤的方案。

## 二、结果

脚本先和真实 `LaunchDetector.add_candle` 对拍：3 组参数 × 5 个合约 × 30 天，提醒时刻、方向、波次全部一致。
开发期 1218 天，样本外 657 天（2026-10-01 ~ 10-07 没有数据，那几天按空仓计）。下面的夏普都已年化（日夏普 × √365），
「每条得分」是 15 种入场、出场组合平均、已扣 0.2% 成本的单笔收益。

### 1. 开发期选出的方案

| | 放量上涨 | 放量下跌 |
|---|---|---|
| 窗口 / 基准期 | 3 分钟 / 180 分钟 | 10 分钟 / 720 分钟 |
| 量比 | ≥ 5 | ≥ 8 |
| 窗口成交额 | ≥ 30 万 | ≥ 100 万 |
| 涨跌幅 | 3% ~ 8% | 3% ~ 8% |
| 突破 | 不要求 | 不要求 |
| 24 小时成交额 | > 500 万 | 不限 |
| 冷却 / 再推进 | 60 分钟 / 8% | 60 分钟 / 8% |
| 回吐比例上限（新参数） | 0.5 | 不限 |

前几名基本都卡在候选族的边上（量比、成交额取最严，冷却取最长，上限取 8%），每天的提醒数贴着 2 条的活跃度下限：
提醒越少越不亏。也就是说，这个族里只要放宽条件、多报几条，得分就往下走。

### 2. 逐项判据

| 判据 | 放量上涨 | 放量下跌 |
|---|---|---|
| 开发期夏普（每天提醒数） | 0.38（3.6 条） | 0.14（2.3 条） |
| 开发期每条得分 | +0.21% | −0.41% |
| 开发期 PSR(夏普 > 0)，不做多重检验校正 | 0.76 | 0.60 |
| ② Deflated Sharpe（预期最大夏普 9.97 / 14.8） | ≈ 0 ✗ | ≈ 0 ✗ |
| ③ PBO（16 段 CSCV） | 0.00 ✓ | 0.00 ✓ |
| ④ 样本外夏普 / PSR | −3.28 / 0.00 ✗ | 1.25 / 0.956 ✓ |
| ④ 样本外每条得分（延迟 0 / 1 / 3 分钟） | −0.36% / −0.33% / −0.30% ✗ | +0.17% / +0.19% / +0.14% ✓ |
| ⑤ 样本外夏普对比现行配置 | −3.28 > −8.77 ✓ | 1.25 > −2.57 ✓ |
| **结论** | **不通过** | **不通过（只差 Deflated Sharpe）** |

- 两个方向的 Deflated Sharpe 都约等于 0。不做任何多重检验校正时，开发期的 PSR 也只有 0.76 和 0.60，开发期本身就不显著。
  预期最大夏普这么高，是因为候选之间差别很大（大部分候选是明显的负数）；就算换更宽松的扣除方式，也过不了不校正这一关。
- PBO 为 0 不代表方案有效：族里大部分候选明显为负，靠前的候选在任何切分下都排在中位数之上，PBO 只说明排序稳定，不说明收益为正。
- 放量下跌的样本外是正的，但开发期每条得分是负的（−0.41%）。开发期的夏普为正，只是因为按天平均：提醒少的日子好、全市场暴跌提醒多的日子差。
  两段数据给出的结论相反，不足以说明有稳定优势。

### 3. 现行配置（对照）

| | 开发期夏普 | 开发期每条得分 | 开发期每天提醒 | 样本外夏普 | 样本外每条得分 | 样本外每天提醒 |
|---|---|---|---|---|---|---|
| 放量上涨 | −6.54 | −0.18% | 20.5 | −8.77 | −0.48% | 43.8 |
| 放量下跌 | −8.06 | −0.55% | 29.2 | −2.57 | −0.02% | 52.1 |

现行配置在开发期的排名：上涨在 128,647 个满足活跃度的候选里排第 95,214，下跌在 130,271 个里排第 88,640。
如果按「跟着提醒方向做一笔」来衡量，现行的提醒在两段数据里都明显为负：提醒之后价格整体上不延续，扣成本后是亏的。

### 4. 结论

按预先写定的判据，**两个方向在这个候选族里都没有通过过拟合检验的方案**，不推荐把上面任何一组写进配置。
按规则不降级保留、不改用第二名。

- 放量上涨：开发期选出的方案在样本外每条都亏（−0.33%），只是比现行配置亏得少（提醒少得多）。
- 放量下跌：样本外成立、也优于现行配置，只差 Deflated Sharpe 这一项；但开发期每条得分为负，两段结论相反。按规则剔除，是否作为例外采用由用户决定。
- 更值得注意的是：在这个衡量方式下，「量价同时启动之后会延续」本身就不成立，扣成本后几乎所有候选都在 0 附近或更差。
  参数调整只能减少亏损，做不出稳定的正收益。提醒如果用于「看到启动、跟进」，现在的提醒量偏多；
  如果只是告诉用户「这个币正在放量异动」，这个衡量方式本身就不适用，需要另外定义好坏，重新预先写定判据再测。

结果文件：`data/backtest/results/launch_grid/select.json`（开发期选参、DSR、PBO、前 30 名）、`evaluate.json`（样本外）。

# 第二轮：按提醒本身的好坏（2026-10-19，用户要的是提醒，不跟着做一笔）

第一轮按「跟着提醒做一笔」计分，不符合用途，作废，结论不用。本轮换成提醒的好坏：报出来的是不是真行情（准），
快速的大行情有没有在前半段报到（全、早）。数据、划分、判定逻辑、候选族都与第一轮相同（第 2~4 节），只换度量和判据。
第一轮只对 4 组参数（两轮选中方案与现行配置）看过样本外，用的是另一种度量，不影响本轮挑选。

## 三、第二轮预先写定的口径与判据（跑数之前写下，之后不改）

### 1. 准：提醒之后价格是否继续走

提醒价 p（提醒那根 K 线收盘价）之后 H 分钟内，价格先沿提醒方向走到 p × (1 ± X)，没有先反向走到 p × (1 ∓ X)，这条提醒算准
（按每分钟最高、最低价判断；同一分钟两边都碰到算不准；H 分钟内两边都没碰到也算不准，说明之后没有像样的延续）。
X ∈ {3%, 5%}，H ∈ {60, 240} 分钟，4 种设置。之后 240 分钟里有没有数据的提醒不计入准确率。

准确率 P = 4 种设置准确率的平均。

### 2. 全、早：快速大行情有没有在前半段报到

- 大行情：每个合约的 1 分钟收盘价做之字线，反转门槛 G/2（上涨段里从最高收盘回落 G/2 才算结束，下跌段反之），
  得到交替的上涨段、下跌段。上涨段涨幅 ≥ G（下跌段跌幅 ≥ G）、从起点到终点不超过 24 小时、段内成交额 ≥ 100 万 USDT、
  全段有数据，记一次该方向的大行情。G ∈ {10%, 20%}。
- 报到：段内（起点之后、终点之前含终点）有同方向的提醒，且提醒价离起点的对数涨跌幅不超过整段的一半，即在前半段就报出来。
- 召回率 R = 两种 G 召回率的平均。大行情按起点所在的周计入。

### 3. 选参指标

**开发期 F1 = 2PR / (P + R)**。不设活跃度下限：报得太少召回低，报得太多准确率低，F1 自己平衡。

### 4. 过拟合判据（全部满足才推荐，没达标直接剔除、不降级、不改用第二名）

对照（基准）一律是现行 `default.yaml` 该方向的取值（第一轮第 5 条）。

1. **只用开发期选参**：开发期 F1 最高的一组，只此一组。
2. **多重检验校正**：F1 不是夏普，Deflated Sharpe 不适用，改用 White's Reality Check：开发期按周做循环块自助法
   （块长 4 周、2000 次），检验「147,456 组里最好的一组 F1 高于现行配置」是否只是挑选运气，p < 0.05。
3. **PBO < 0.5**：开发期的周按时间切成 16 段做 CSCV，按 F1 排名。
4. **样本外成立**：样本外 F1 高于现行配置，按周的循环块自助法单侧 p < 0.05；且 4 种「准」设置 × 2 种 G 共 8 种组合
   各自算的 F1 都高于现行配置。

不测试任何按一天中时段过滤的方案。

## 四、第二轮结果

脚本：`launch_alerts.py`（`selftest` 用手造价格检查之字线与准不准；冷却、再推进沿用第一轮已对拍的实现；
选中方案的 F1 用网格与单组评估两套实现各算一遍，一致）。开发期 174 周，样本外 94 周。
开发期大行情：上涨 ≥10% 22,479 段、≥20% 5,487 段；下跌 ≥10% 19,240 段、≥20% 3,350 段。

跑数过程中发现 PBO 的 numba 实现有错（在元组循环里写数组，写不回原数组，每个切分都得到 logit 0，PBO 恒为 1），
改正后与 numpy 逐切分核对一致再重跑；只改了计算错误，口径与判据没动。

### 4. 结论与代价

按预先写定的判据，两个方向都选出了通过检验的一组（上表第 1 节）。F1 的提升几乎全部来自召回率：
样本外 ≥20% 的大行情在前半段报到的比例从约 25% 翻倍到 51%~54%；下跌的准确率不变，上涨的准确率从 0.437 降到 0.384。

代价是提醒量：样本外每天上涨约 130 条、下跌约 114 条，合计约为现行的 2.6 倍。F1 把准确率与召回率看得一样重，
没有计入看提醒的精力成本；最优解又落在候选族最宽的边上，说明按 F1 再放宽可能还会更高。
如果每天能看的提醒有上限，这组参数不适用，应先定下可接受的提醒量（或给准确率更大权重，如 F0.5），再预先写定判据重跑。

# 第三轮：更看重准确率（2026-10-19，用户要求）

第二轮的 F1 把准确率和召回率看得一样重，选出的方案提醒量大、上涨准确率反而下降。用户更看重准确率，本轮只换选参指标，
数据、划分、候选族、「准」与「大行情报到」的定义都与第二轮相同，直接用第二轮的逐周计数。
第二轮已对其选中方案与现行配置看过样本外（F1 口径），本轮选参只用开发期，不参考那些数字。

## 五、第三轮预先写定的判据（跑数之前写下，之后不改）

1. **选参指标：开发期 F0.5** = 1.25 × P × R / (0.25 × P + R)，P、R 同第二轮。只选开发期 F0.5 最高的一组。
2. **Reality Check**（同第二轮做法，指标换成 F0.5）p < 0.05。
3. **PBO < 0.5**（同第二轮做法，按 F0.5 排名）。
4. **样本外**：F0.5 高于现行配置，自助法单侧 p < 0.05；8 种设置组合的 F0.5 逐一高于现行配置。
5. **样本外准确率不低于现行配置**（用户更看重准确率，选出的方案不能比现在更不准）。

另算一个只供解读、不作判据的参照：随机时刻的准确率。每个合约每隔 61 分钟取一个时刻（之后 240 分钟有数据、
前 24 小时成交额 > 100 万），按同样的 4 种设置分别假设「上涨提醒」「下跌提醒」算准确率，说明提醒比随便挑个时刻准多少。

## 六、第三轮结果

`select --beta 1` 先重跑一遍，第二轮的数字完全复现，再按 F0.5 选参（结果 `select_b0.5.json`、`evaluate_b0.5.json`、`baseline.json`）。

### 1. 开发期选出的方案

| | 放量上涨 | 放量下跌 |
|---|---|---|
| 窗口 / 基准期 | 5 / 180 分钟 | 5 / 180 分钟 |
| 量比 / 窗口成交额 | ≥ 2 / ≥ 5 万 | ≥ 2 / ≥ 5 万 |
| 涨跌幅 | ≥ 3%，不设上限 | 3% ~ 15% |
| 突破 | 不要求 | 不要求 |
| 24 小时成交额 | > 100 万 | > 100 万 |
| 冷却 / 再推进 | 15 分钟 / 3% | 15 分钟 / 3% |
| 回吐比例上限（新参数） | 不限 | 不限 |

与第二轮相比只是涨跌幅下限从 2% 提到 3%、加了 24 小时成交额 > 100 万。量比、窗口成交额调严并不能让提醒更准，
所以 F0.5 仍把它们放在最宽的一端（提高它们只会少报，准确率不升）。

### 2. 逐项判据

| 判据 | 放量上涨 | 放量下跌 |
|---|---|---|
| 开发期 F0.5（准确率 / 召回率 / 每天提醒） | 0.379（0.392 / 0.336 / 30.7） | 0.350（0.356 / 0.325 / 26.4） |
| 现行配置开发期 F0.5（准确率 / 召回率 / 每天提醒） | 0.340（0.398 / 0.215 / 20.5），排第 1,396 | 0.296（0.307 / 0.258 / 29.2），排第 4,769 |
| ② Reality Check p | 0.010 ✓ | 0.0085 ✓ |
| ③ PBO | 0.00 ✓ | 0.00 ✓ |
| ④ 样本外 F0.5 vs 现行 | 0.398 vs 0.343，p < 0.0005 ✓ | 0.395 vs 0.310，p < 0.0005 ✓ |
| ④ 8 种设置组合逐一高于现行 | 8 / 8 ✓ | 8 / 8 ✓ |
| ⑤ 样本外准确率不低于现行 | 0.430 < 0.437 ✗ | 0.409 > 0.359 ✓ |
| **结论** | **不通过，维持现行配置** | **通过** |

### 3. 样本外细项

| | 上涨·选中 | 上涨·现行 | 下跌·选中 | 下跌·现行 | 随机时刻 |
|---|---|---|---|---|---|
| 准确率（4 种设置平均） | 0.430 | 0.437 | 0.409 | 0.359 | 0.113（涨）/ 0.111（跌） |
| 3% 内 240 分钟先到 | 0.483 | 0.485 | 0.478 | 0.455 | 0.220 / 0.228 |
| ≥10% 大行情前半段报到 | 19.5% | 12.1% | 21.1% | 14.8% | |
| ≥20% 大行情前半段报到 | 41.8% | 24.7% | 48.9% | 25.4% | |
| 每天提醒（其中第 1 波） | 72（49） | 44（29） | 69（53） | 52（44） | |

随机时刻的准确率低，主要是因为平常多数时候 60~240 分钟内走不出 ±3%~5%（两边都没碰到算不准）；
提醒的准确率约为随机时刻的 3.6~3.8 倍。

### 4. 结论

- 放量上涨：维持现行配置。选中方案多报到大行情，但样本外准确率略低（0.430 vs 0.437），
  不满足用户最看重的这一条。
- 放量下跌：改用上表的一组。样本外准确率从 0.359 提到 0.409，≥20% 大行情前半段报到从 25% 提到 49%，
  代价是每天多约 17 条（52 → 69）。现行代码里窗口成交额、基准期、冷却、再推进、合约池门槛两个方向共用，
  下跌要用这组而上涨保持不变，需要把这些项也做成下跌可单独设置。

# 第四轮：涨跌幅从窗口极值算起（2026-10-31，用户要求）

实盘的涨跌幅是「窗口前一根收盘 → 最后一根收盘」。用户问能否改成从窗口内最低价（上涨）/ 最高价（下跌）算起。
本轮比较两种口径哪个提醒更好，只回答口径问题，不借机改其他参数。

## 七、第四轮预先写定的口径与判据（跑数之前写下，之后不改）

### 1. 两种口径

- **收盘口径（现行）**：起点价 = 窗口前一根收盘。
- **极值口径**：上涨的起点价 = min(窗口前一根收盘, 窗口内各分钟最低价)，下跌 = max(窗口前一根收盘, 窗口内各分钟最高价)。
  算上前一根收盘，是为了让涨跌幅不会小于收盘口径，两者只差「窗口内先反向走、再拉回来」的那一段。
  同一分钟可能同时够上涨和下跌，两个方向各算各的。

涨跌幅门槛、涨跌幅上限（插针保护）、回吐比例都按各自口径的涨跌幅算；量比、窗口成交额、突破、冷却、再推进与第二轮相同。

### 2. 数据与划分

只用最近两年：2024-10-01 ~ 2026-09-29（UTC，正好 104 周，不下载新数据）。
开发期为前 78 周（到 2026-03-31），样本外为后 26 周（2026-03-31 ~ 2026-09-29）。
候选族、「准」与「大行情前半段报到」的定义都与第二轮相同。之前的轮次用的是 2021-09 起的数据，那里的结论这次不参考。

### 3. 选参与判据（每个方向分别判断，全部满足才说极值口径更好，没达标就维持收盘口径）

选参指标沿用第三轮的 F0.5（用户更看重准确率）。两种口径各自在开发期跑全量网格，各选开发期 F0.5 最高的一组
（分别记为「收盘选中」「极值选中」）。对照「现行」是 `config/default/launch.yaml` 该方向的取值（收盘口径）。

1. **Reality Check**（同第二轮做法）：极值口径的族里最好的一组比现行配置好，p < 0.05。
2. **PBO < 0.5**：极值口径的族，开发期 16 段 CSCV。
3. **样本外比收盘选中好**：极值选中的样本外 F0.5 高于收盘选中，按周的循环块自助法单侧 p < 0.05；
   且 4 种「准」设置 × 2 种 G 共 8 种组合的 F0.5 逐一高于收盘选中。
4. **样本外准确率不低于收盘选中**。

另外列出现行配置在两种口径下的样本外结果（参数相同，只换口径）。这一项只供解读，不作判据。
收盘口径在这两年里选出的参数是否该替换现行配置，不在本轮回答。

## 八、第四轮结果

脚本：`launch_alerts.py --span 2y --start close|extreme`，最后用 `compare` 比较。`selftest` 用手造价格检查了极值口径的抽取。
另外在 PEPE、TRB 上核对过：两年区间单独抽取的结果与全段抽取后截取的完全一致（成交额只差 1e-10 量级的浮点误差）；
同一组参数下，收盘口径的候选都包含在极值口径里，且涨跌幅不变小。
开发期 78 周，样本外 26 周。大行情：上涨 ≥10% 30,841 段、≥20% 11,014 段；下跌 ≥10% 27,956 段、≥20% 7,154 段
（抽取范围内全部，开发期与样本外按周再分）。

### 1. 开发期选出的方案

两种口径选出的参数**完全相同**（两个方向也只差回吐比例）：窗口 5 / 基准期 180 分钟、量比 ≥ 2、窗口成交额 ≥ 5 万、
涨跌幅 ≥ 3%、不要求突破、24 小时成交额 > 100 万、冷却 15 分钟、再推进 3%；上涨不设涨跌幅上限、不限回吐比例，
下跌不设上限、回吐比例 ≤ 0.5。所以下面的比较就是同一组参数只换口径。

### 2. 逐项判据（极值选中 vs 收盘选中）

| 判据 | 放量上涨 | 放量下跌 |
|---|---|---|
| ① Reality Check p（极值口径的族 vs 现行参数，见下注） | < 0.0005 ✓ | 1.0 ✗（现行参数在极值口径的族里排第 5，没有明显更好的） |
| ② PBO | 0.00 ✓ | 0.00 ✓ |
| ③ 样本外 F0.5 | 0.417 vs 0.416，自助法 p = 0.43 ✗ | 0.413 vs 0.422，p = 1.0 ✗ |
| ③ 8 种设置组合逐一更高 | 4 / 8 ✗ | 1 / 8 ✗ |
| ④ 样本外准确率不低于收盘选中 | 0.438 < 0.449 ✗ | 0.417 < 0.431 ✗ |
| **结论** | **不更好，维持收盘口径** | **不更好，维持收盘口径** |

注：第七节写定 ① 的对照是收盘口径下的现行配置，但 `select --start extreme` 实际用的是同一组现行参数换成极值口径
（开发期 F0.5：上涨 0.339、下跌 0.378；收盘口径下是 0.340、0.381），与写定的不一致。按写定的对照看，
上涨的族里最好的一组 0.391 仍远高于 0.340；下跌最好的一组 0.380 低于 0.381，① 同样不通过。
而且 ③④ 两个方向都不通过，结论不受影响，所以没有重跑。

### 3. 样本外细项

| | 上涨·收盘选中 | 上涨·极值选中 | 下跌·收盘选中 | 下跌·极值选中 |
|---|---|---|---|---|
| 准确率（4 种设置平均） | 0.449 | 0.438 | 0.431 | 0.417 |
| ≥10% / ≥20% 大行情前半段报到 | 21.2% / 43.2% | 24.1% / 45.8% | 25.3% / 52.6% | 26.8% / 52.6% |
| 每天提醒（其中第 1 波） | 67.5（42.5） | 89.8（56.1） | 68.8（48.9） | 85.7（59.2） |

现行配置只换口径（只供解读）：上涨准确率 0.457 → 0.441、每天 40 → 54 条；下跌 0.430 → 0.417、每天 69 → 86 条。

### 4. 结论

从窗口极值算涨跌幅，多报出来的都是「窗口内先反向、再拉回」的情况。这些提醒比现行口径的更不准，
两个方向的准确率都下降约 1~1.5 个百分点，每天多出约 17~22 条（多 25%~33%）；
大行情前半段报到的比例只多 0~3 个百分点。上涨的 F0.5 持平，下跌的更低。两个方向都维持现行的收盘口径。
之后按用户要求，把极值口径做成了配置项 `launch.<方向>.change_from_window_extreme`。代码默认与 `config/default/launch.yaml`
都关闭，判定与之前完全相同。

收盘口径在这两年里选出的上涨参数与第三轮选中的一组相同（第三轮因样本外准确率略低未采用），本轮不回答是否替换。

结果文件：`data/backtest/results/launch_alerts_2y/`、`launch_alerts_2y_extreme/`（`select_b0.5.json`、`evaluate_b0.5.json`，
后者另有 `compare_b0.5.json`），日志 `launch_round4.log`。
